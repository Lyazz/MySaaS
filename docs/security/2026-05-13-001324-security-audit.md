# Swekly SaaS — Security Audit Report

**Report ID:** 2026-05-13-001324-security-audit
**Date:** 2026-05-13
**Branch:** repo-reset-2026-01-25
**Scope:** Full codebase — Nuxt 3 frontend (SSR), Express.js backend (`backend/src/`), Prisma 5.22 ORM, S3/MinIO, Capacitor mobile.
**Reviewer:** Security Audit (automated, methodology: OWASP ASVS L2 + multi-tenancy threat model)

---

## Executive Summary

The Swekly codebase shows a mature multi-tenant posture with consistent manual `tenantId` scoping across Prisma queries, helmet headers, tenant-aware rate limiting, password hashing via bcrypt, HMAC-verified delivery webhooks, and a centralized rich-text sanitizer. The audit found no SQL injection vectors, no critical tenant cross-leakage in admin-facing modules, and HS256 JWT verification with explicit algorithm allowlist for the main access token.

However, several material weaknesses remain. **Critical findings cluster around three areas:** (1) the super-admin `impersonate` endpoint returns the target user's `passwordHash` and does not issue a scoped/short-lived impersonation token; (2) the local-file token verifier (used to deliver private billing proofs and similar tenant artifacts) accepts any JWT algorithm because `jwt.verify` is called without an `algorithms` allowlist, opening an algorithm-confusion path that the access-token verifier defends against; (3) the `auth.middleware` does not enforce that the JWT's `tenantId` matches the host-derived tenant, allowing a token issued for tenant A to be used on tenant B's storefront for any admin endpoint reachable from the SaaS host. A defense-in-depth Prisma extension (`getTenantPrisma`) is implemented in `backend/src/lib/prisma.ts` but **never used** — all tenant isolation depends on developer discipline.

High-severity issues include: weak registration phone-allowlist bypass via environment toggle, missing CSRF for cookieless API (acceptable for Bearer tokens but worth confirming), Helmet `contentSecurityPolicy` disabled, public order endpoint trusting client-supplied `shippingAmount`, public Pixel detect-chats endpoint that accepts arbitrary bot tokens (SSRF-by-proxy to `api.telegram.org`), and several IDOR-adjacent patterns where `findUnique({ where: { id } })` is performed before a manual tenant check (works correctly on Prisma 5.22 because `WhereUniqueInput` accepts non-unique filters, but two call-sites still pass only `id`).

Overall risk: **Medium-High**. Two critical findings should be remediated before the next production deploy; four high-severity items in the next sprint.

## Methodology

1. **Static code review** of `backend/src/`, `server/api/`, `prisma/schema.prisma`, `components/storefront/`, and `package.json`.
2. **Threat model focus areas** per request: tenant isolation (every Prisma query traced through controller → service), authentication/authorization (JWT, RBAC middleware coverage), injection (raw SQL, SSRF in delivery providers, command injection, SSTI), input validation/mass assignment, API security (IDOR, rate limiting, CORS, headers), business logic (race conditions in orders/cash/pos, price manipulation), data protection (secret handling, encryption at rest, timing-safe comparisons), supply chain (`package.json` direct dependencies), storefront SSR (XSS via `v-html`), configuration.

4. **Tools available:** read-only access to source. `package-lock.json` not inspected per scope. No runtime testing performed.
5. **Severity scale** (1.0–10.0): Critical ≥ 9.0 — exploitable in production, leads to multi-tenant data breach or full account takeover; High 7.0–8.9 — exploitable with attacker effort or partial impact; Medium 4.0–6.9 — exploitable only with privileged access or chained; Low < 4.0 — hardening / hygiene.

#### C-001 — Super-admin impersonation returns full user object including `passwordHash` and does not issue an impersonation token

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/modules/tenants/routes.ts`
**Lines:** 272–307
**Risk score:** 9.4 / 10.0

**Vulnerable code:**
```ts
router.post('/:id/impersonate', async (req, res) => {
    const targetUser = await prisma.user.findFirst({
        where: { tenantId: id, role: 'owner' }
    })
    if (!targetUser) { ... }
    await logAction({ action: 'IMPERSONATE_USER', ... })
    res.json({ success: true, impersonatedUser: targetUser })
})
```

`targetUser` is returned **with `passwordHash` and `tokenInvalidBefore`** because no `select` clause is applied and no destructuring is done before `res.json`. A super-admin (or anyone who compromises a super-admin session) can pull bcrypt hashes for every tenant owner and crack them offline. The endpoint also does not return an impersonation token — implying the frontend logs in by other means — which suggests the password hash may itself be the impersonation primitive in the client flow.

Furthermore, the audit log records the action but not the originating IP or user-agent, and there is **no time-boxed impersonation token** (the spec requires impersonation to be audit-logged and scoped). The action is irreversibly performed even if the request is replayed.

**Impact:** Mass disclosure of all tenant-owner password hashes from a single privileged endpoint. Compromise of a super-admin account becomes equivalent to compromise of every tenant owner.

**Remediation:**
```ts
const targetUser = await prisma.user.findFirst({
    where: { tenantId: id, role: 'owner' },
    select: { id: true, email: true, role: true, tenantId: true, name: true }
})
if (!targetUser) return res.status(404).json(...)

const impersonationToken = signAccessToken(
    { userId: targetUser.id, tenantId: id, role: targetUser.role, impersonatedBy: adminUser.id },
    { expiresIn: '15m' }
)
await logAction({
    action: 'IMPERSONATE_USER',
    details: JSON.stringify({ ip: req.ip, ua: req.get('user-agent'), targetUser: targetUser.email }),
    userId: adminUser.id, targetId: targetUser.id, tenantId: id
})
res.json({ success: true, impersonatedUser: targetUser, token: impersonationToken })
```
Also: add a server-side `impersonatedBy` claim and reject mutations on the most sensitive paths (e.g. password change, payouts) when an access token carries `impersonatedBy`.

#### C-002 — Local-file JWT verifier accepts any algorithm (algorithm-confusion / `alg=none`)

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/lib/local-file-token.ts`
**Lines:** 28–35
**Risk score:** 9.2 / 10.0

**Vulnerable code:**
```ts
export const verifyLocalFileToken = (token: string): LocalFileTokenPayload => {
    const secret = requireJwtSecret()
    const decoded = jwt.verify(token, secret) as any   // no { algorithms: [...] }
    ...
}
```

Unlike `verifyAccessToken` in `backend/src/lib/jwt.ts` (which correctly pins `algorithms: ['HS256']`), this helper omits the option entirely. `jsonwebtoken@9` did patch the historical `alg=none` bypass, but the verifier **still accepts any algorithm the library knows** when not pinned, so a publicly-known asymmetric key (or any leakage of an RS256 public key the JWT secret happens to equal) becomes an arbitrary-file-read primitive. Tokens minted here grant direct read access to anything under `BASE_DIR = process.cwd() + '/private_uploads'` including billing payment proofs, which can contain CCP/Baridimob screenshots and PII.

These tokens are returned from super-admin endpoints (`billing-admin.service.ts:148`) and used by `/api/files/local?token=…` with **no further tenant or auth check** — the JWT alone is the capability.

**Impact:** Forging this token grants cross-tenant read of any payment proof / arbitrary path under `private_uploads` for any attacker who can produce a JWT the library accepts.

**Remediation:**
```ts
export const verifyLocalFileToken = (token: string): LocalFileTokenPayload => {
    const secret = requireJwtSecret()
    const decoded = jwt.verify(token, secret, { algorithms: ['HS256'] }) as any
    if (!decoded || decoded.kind !== 'local-file' || typeof decoded.key !== 'string') {
        throw new Error('Invalid token')
    }
    return decoded
}
```
Additionally, sign the token with `algorithm: 'HS256'` explicitly in `signLocalFileToken` (currently relies on library default) and consider binding the token to a tenant ID claim that the download handler cross-checks against the requesting session (or simply require authentication on `/api/files/local` and embed `tenantId` in the token payload, validated server-side).

#### C-003 — Auth middleware does not enforce token `tenantId` matches host-derived `req.tenant`

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/middleware/auth.middleware.ts`
**Lines:** 28–49
**Risk score:** 9.0 / 10.0

**Vulnerable code:**
```ts
const user = await prisma.user.findFirst({
    where: {
        id: decoded.userId,
        ...(decoded.tenantId ? { tenantId: decoded.tenantId } : {}),
        isActive: true
    }
})
if (user) {
    ...
    req.user = user
    // Also enforce tenant context if mismatch?
    // The middleware/tenant.ts sets req.context.tenant
    // We could check if user.tenantId === req.context.tenant.id
}
```

The TODO comment confirms it: `auth.middleware` looks up the user by their **own** `tenantId` from the JWT but never compares that to the host-derived `req.tenant` resolved by `expressTenantMiddleware`. The only place this check exists is **inside** `requireTenantRoles` (`rbac.middleware.ts:39`), which guards admin routes. **Public** tenant-scoped routes (storefront product list, public order creation, pixel payload, loyalty summary) only call `expressTenantMiddleware` plus `expressAuthMiddleware`; they never invoke `requireTenantMember` / `requireTenantAdmin`. As a result, a logged-in user from tenant A whose Bearer token rides on a request to tenant B's storefront will have `req.user` populated with their tenant-A identity while `req.tenant` is tenant B. Most downstream handlers use `req.tenant.id` correctly, but `req.user.id` is accepted by code that records `createdByUserId` in audit/loyalty ledger writes (e.g. `orders.controller.ts:155`, `OrdersService.applyCarrierStatus`, `updateUnconfirmed`, `markRead`). This produces incorrect audit attribution **and** allows the attacker's user record to be silently attached to a victim tenant's resources.

Worse, if any future admin module mounts under a path that bypasses `requireTenantMember` (the routes.ts pattern is large and easy to miss), the auth middleware alone is not safe to rely on for tenant boundary.

**Impact:** Tenant boundary depends entirely on every admin route correctly applying `requireTenantMember`. A single forgotten guard leaks across tenants because `auth.middleware` itself does not enforce the boundary.

**Remediation:** Make the host/token mismatch explicit in `auth.middleware`:
```ts
if (user) {
    if (req.tenant && user.tenantId !== req.tenant.id && !user.isSuperAdmin) {
        // Token issued for another tenant on this host — refuse to attach req.user.
        return next()
    }
    req.user = user
}
```
And adopt `getTenantPrisma(req.tenant)` from `backend/src/lib/prisma.ts:33` as the only prisma client surfaced to services — it auto-injects `tenantId` on create/update/delete and converts `findUnique` to a tenant-scoped `findFirst`. It is currently dead code.

#### H-001 — Helmet `contentSecurityPolicy` is disabled

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/app.ts`
**Line:** 27
**Risk score:** 7.6 / 10.0

```ts
helmet({
    contentSecurityPolicy: false,
    ...
})
```

CSP is the strongest mitigation against XSS on the admin dashboard and storefront SSR pages. With it disabled and rich-text content rendered through `components/common/SafeRichText.vue` (uses `v-html`) and product images served from S3/MinIO and arbitrary tenant-owned domains, any sanitizer regression becomes immediately exploitable. The backend also serves user-uploaded files through `/api/files/local` without a CSP `default-src` to fall back on.

**Impact:** Stored XSS in tenant rich-text (description, etc.) is partially mitigated by `sanitize-html`, but with no CSP the attack surface for clipboard/keylogger/credential-stealing payloads is unbounded if any sink is missed.

**Remediation:** Enable a strict CSP. Storefront pages need `script-src 'self'` plus a tenant pixel allowlist; admin pages can use `script-src 'self' 'nonce-...'`. Allow `img-src https:` for S3/MinIO/customer domains:
```ts
helmet({
    contentSecurityPolicy: {
        directives: {
            defaultSrc: ["'self'"],
            scriptSrc: ["'self'", "https://connect.facebook.net", "https://www.googletagmanager.com"],
            imgSrc: ["'self'", "https:", "data:"],
            connectSrc: ["'self'", "https://api.telegram.org"],
            frameAncestors: ["'none'"]
        }
    },
    ...
})
```

#### H-002 — Public order creation trusts client-supplied `shippingAmount` and `shippingCurrency`

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/modules/orders/orders.controller.ts`
**Lines:** 408–424 (public path)
**Risk score:** 8.1 / 10.0

```ts
const result = await service.createPublicOrder({
    tenantId: tenant.id,
    ...
    shippingAmount: req.body?.shippingAmount,
    shippingCurrency: req.body?.shippingCurrency,
    ...
})
```

The shipping price is taken directly from the request body and incorporated into `totalAmount` (`orders.service.ts:145` `computeTotalWithShipping`). For a public, unauthenticated checkout endpoint, this is a price-manipulation vector — an attacker can submit a **negative** `shippingAmount` to reduce the total, or zero to skip shipping. While `shippingAmount` is stored alongside the order and presumably reconciled with the delivery provider on confirmation, the **stored total** is what the merchant sees in their dashboard and reports.

**Impact:** Public buyer can submit orders with arbitrary shipping totals, distorting revenue analytics, undermining COD reconciliation, and on some templates causing the loyalty-points engine (which uses `totalAmount` as input) to mint extra customer points.

**Remediation:** Server-side rate quote. On public order create, recompute shipping from tenant rate cards plus the wilaya/commune resolution server-side (the data is already present in `delivery.service.ts`). Reject `shippingAmount < 0` unconditionally and ignore any client value when a server-side rate exists:
```ts
const quote = await deliveryService.quote({ tenantId, wilayaCode, communeCode, deliveryMode, provider })
const shippingAmount = quote.amount   // not req.body.shippingAmount
```

#### H-003 — Public `detect-chats` endpoint proxies arbitrary Telegram bot tokens to `api.telegram.org`

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/modules/integrations/integrations.controller.ts`
**Lines:** 97–116; route at `/Users/lyazz/Documents/js projects/MySaaS/backend/src/modules/integrations/routes.ts:15`
**Risk score:** 7.5 / 10.0

```ts
const botToken = typeof botTokenRaw === 'string' ? botTokenRaw.trim() : ''
...
const result = await telegramService.detectChats(botToken)
```

While routed behind `requireTenantMember` + `requireStaffCrud('integrations')`, the handler accepts a fully attacker-controlled bot token and uses it to call `https://api.telegram.org/bot${botToken}/${method}`. The URL is built with `new URL()` so path traversal in `method` (passed via `telegramGet`) is mitigated, but the **token** segment is interpolated directly. An attacker who can pass a token containing `../`, slashes, or URL-encoded query characters can pivot the request to a different endpoint on `api.telegram.org`. Combined with HTTP redirect behavior (Telegraf's underlying `fetch` follows redirects by default in Node), this becomes a constrained SSRF against `api.telegram.org` and any host its TLS certificate accepts.

**Impact:** Limited SSRF against Telegram. More importantly, the endpoint is also a credential-oracle — by enumerating responses, an attacker with staff-level access can validate stolen Telegram bot tokens of any organization.

**Remediation:** Strictly validate bot-token shape (`^\d+:[A-Za-z0-9_-]{30,}$`) before constructing the URL; reject anything else with 400:
```ts
if (!/^\d+:[A-Za-z0-9_-]{30,}$/.test(botToken)) {
    return res.status(400).json({ statusCode: 400, statusMessage: 'Invalid bot token format' })
}
```
Apply the same regex in `saveIntegration` for `TELEGRAM`. Disable redirect-following on the underlying `fetch` to Telegram. Also rate-limit this route per-tenant; currently it falls under the generic 1k/15min `apiRateLimiter` which is far too permissive for a credential-validation oracle.

#### H-004 — JWT access token TTL defaults to 7 days with no refresh-token rotation

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/lib/jwt.ts`
**Lines:** 3, 13–22
**Risk score:** 7.2 / 10.0

```ts
const DEFAULT_ACCESS_TOKEN_TTL: SignOptions['expiresIn'] = '7d'
```

A 7-day access token without refresh-token rotation means a stolen token is valid for a week. The codebase does have a `tokenInvalidBefore` cutoff (see `auth.middleware.ts:38` and `auth/routes.ts` logout), so a server-side revoke is possible, but the default expiration is far longer than industry practice (15m access token + 7d refresh token with rotation).

**Impact:** A leaked JWT (via XSS, log exposure, malicious browser extension, mobile-storage exfiltration on Capacitor) is usable for a full week. The 30-day storefront export tokens / staff sessions amplify this.

**Remediation:** Adopt a 15-minute access token + httpOnly refresh-cookie pattern with refresh-token rotation; persist `refreshTokenJti` per session and invalidate on rotation. At minimum, lower `DEFAULT_ACCESS_TOKEN_TTL` to `'2h'` and document the trade-off.

#### H-005 — `req.tenant` resolved from `X-Forwarded-Host` without verifying trusted proxy chain

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/middleware/tenant.middleware.ts`
**Lines:** 6–7
**Risk score:** 7.0 / 10.0

```ts
const trustProxy = process.env.TRUST_PROXY === 'true'
const host = (trustProxy ? req.get('x-forwarded-host') : null) || req.get('host') || ''
```

When `TRUST_PROXY=true`, the middleware blindly trusts `X-Forwarded-Host`. Express's own `trust proxy` is configured at `app.ts:22` (`app.set('trust proxy', 1)`), which trusts the first hop only — fine if the deployment really is behind exactly one trusted reverse proxy. But the tenant middleware here does **not** use `req.hostname` (which respects the `trust proxy` setting). If the real edge passes through more than one hop (CDN → load balancer → app), or if any internal service can speak to the Node process directly, an attacker can submit `X-Forwarded-Host: victim-tenant.swekly.com` and impersonate the host context.

**Impact:** Host-header tenant smuggling — attacker pins their session to a victim tenant's context, then triggers any code path that depends on `req.tenant.id` (e.g. public order creation, public store settings reads, webhook handlers that resolve a `webhookSecret` from `tenantDeliveryAccount`).

**Remediation:** Replace manual header parsing with `req.hostname` (which Express resolves against `trust proxy`):
```ts
const host = req.hostname || req.get('host') || ''
```
Verify the deployment topology: if more than one hop exists, set `app.set('trust proxy', N)` with the correct hop count and confirm internal services cannot reach the Node socket. Add an HSTS-precondition check that the edge always strips client-sent `X-Forwarded-Host` and re-injects its own.

#### H-006 — Registration phone-allowlist relies on `process.env` flag that can be toggled per-deploy

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/modules/auth/routes.ts`
**Lines:** 13, 19–24, 75–85
**Risk score:** 7.0 / 10.0

```ts
const REGISTER_WHITELIST_PHONE = '0540801436'
...
const isTemporaryPhoneLockEnabled = () => {
```

A hard-coded developer phone is the only allowed registrant, gated by an env var that defaults to `true` outside tests. This is fine as a temporary measure but:

#### M-002 — Defense-in-depth Prisma tenant extension exists but is unused

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/lib/prisma.ts`
**Lines:** 33–138
**Risk score:** 6.2 / 10.0

`getTenantPrisma(tenant)` wraps the global Prisma client with a `$extends.query.$allModels.$allOperations` interceptor that auto-injects `tenantId` on create/update/delete and rewrites `findUnique` to a tenant-scoped `findFirst`. It is exported but never imported anywhere. Every service constructs raw queries and remembers to add `tenantId` by hand. This works today but is fragile — see C-003, and the borderline cases below (M-003, M-004).

**Impact:** No active vulnerability today, but the next developer who copy-pastes a `prisma.product.findUnique({ where: { id } })` introduces a cross-tenant read. The extension would have prevented that.

**Remediation:** Make `getTenantPrisma(req.tenant)` available via `req.prisma` in middleware, and gradually migrate services to receive a tenant-bound client instead of importing the global one. Block the global import with an ESLint rule outside of system code.

```ts
const clientId = normalizeClientId(data?.id)
```

#### M-007 — Public storefront pricing computed server-side but bundle deals trust client `quantity`

**File:** `/Users/lyazz/Documents/js projects/MySaaS/backend/src/modules/orders/orders.service.ts`
**Lines:** ~362, ~485, plus the `items` array passed in from `req.body`

## Architecture Assessment

**Multi-tenancy posture (the platform's load-bearing guarantee).** The schema enforces `tenant_id NOT NULL` on tenant-owned tables and pairs compound unique keys like `tenantId_id` so most updates are inherently scoped (e.g. `cash.service.ts:185`, `customers.service.ts:455`, `orders.service.ts:850`). Service code consistently `where: { tenantId }` on `findMany`/`findFirst`/`updateMany`/`deleteMany`. The discipline is good but **manual**. Three pieces of structural strengthening would make tenancy unbreakable:
1. Activate the `getTenantPrisma` extension (M-002) and route every request's services through it.
2. Make `auth.middleware` reject token/host tenant mismatch (C-003) so the boundary is enforced before any handler runs.
3. ESLint-forbid raw `prisma.*` imports outside `backend/src/lib/`.

**Authentication.** JWT HS256 with explicit algorithm pin on the main access-token verifier. Logout invalidates tokens via `tokenInvalidBefore`. Login is rate-limited at 10/15min per tenant+IP. Weaknesses: 7-day TTL (H-004), the local-file token verifier without algorithm pin (C-002), no refresh-token rotation, no MFA on super-admin.

**RBAC.** Three layers — `requireTenantRoles` (`rbac.middleware.ts`), `requireSuperAdmin` (`superadmin.middleware.ts`), and per-resource staff permissions (`staff-permissions.middleware.ts`) with a DB-backed `TenantStaffRolePermission` table. The staff layer maps HTTP method → CRUD action consistently. Owner/admin/staff hierarchy is enforced in `requireTenantRoles` and `requireTenantAdmin = requireTenantRoles(['owner', 'admin'])`.

**Rate limiting.** Tenant-aware composite key (`tenantId:ipKey`) prevents one noisy tenant from exhausting another's quota. Login=10/15min, register=5/hr, public order POST=30/hr, generic API=1000/15min. Reasonable; the register limit is intentionally conservative.

**Delivery provider integrations (Maystro, Yalidine).** Out-bound URLs are env-pinned (`DEFAULT_BASE_URL`), with `baseURL` accepting an env override but never a per-request override. No SSRF surface from request bodies. Retry/backoff and 502 mapping is correct. Webhook authentication: Maystro uses a per-tenant shared secret with header comparison + `timingSafeEqual`; Yalidine uses HMAC-SHA256 over the raw body with `timingSafeEqual`. Both are correct.

**Audit logging.** `expressAuditMiddleware` records every mutating request post-response with redaction of password/token-named fields. Adds `userId`, `tenantId`, status, query, and body. Login/register are skipped (acceptable). Super-admin tenant operations also call `logAction` explicitly. Missing: client IP and user agent are not captured.

**File handling.** Upload is gated by `requireTenantAdmin`, restricts MIME to image/*, optimizes via sharp, persists in S3/MinIO under `tenants/{tenantId}/public/...`, fallback to local in non-prod. Private files (billing proofs) use signed local-file tokens (see C-002).

**SSR/storefront.** `expressTenantMiddleware` resolves tenant via subdomain or `TenantDomain` custom-domain lookup. Public routes are deliberate. `SafeRichText` uses `sanitize-html` for tenant-supplied rich text.

## Technical Recommendations

1. **Adopt the `getTenantPrisma` extension.** Wire it in via Express middleware: after `expressTenantFromUserMiddleware`, attach `req.prisma = getTenantPrisma(req.tenant)` and refactor services to receive a Prisma client from the controller. This converts manual tenant scoping into a structural guarantee (closes C-003 / M-002 / M-003 / M-004 in one move).

2. **Pin JWT algorithms on every `verify` call.** Add an ESLint rule that forbids `jwt.verify(token, secret)` without an options object that contains `algorithms`. Apply to `local-file-token.ts` immediately.

3. **Enable Helmet CSP.** Start with `Content-Security-Policy-Report-Only` for the admin dashboard (`X-Robots-Tag` already excludes API routes from caching, so CSP can land safely). Iterate by route to a non-report policy.

4. **Strip super-admin sensitive fields by `select`.** Add a `userPublicSelect` constant and require every controller returning user data to use it. The impersonation endpoint specifically should never expose `passwordHash`, `tokenInvalidBefore`, `cashboxId`, or any raw `Prisma.User` payload.

5. **Add `algorithms: ['HS256']` to `local-file-token.ts` (and any other `jwt.verify`).** One-line fix, immediate.

6. **Server-side shipping quote on public order create.** Already implemented for admin paths — extract the quote function and call it from `createPublicOrder` instead of trusting `req.body.shippingAmount`.

7. **Telegram bot-token regex.** Reject non-matching tokens before any `fetch`. Disable redirect-following in the Telegram client. Per-tenant per-route rate limit at 10/min on `detect-chats` and `/test`.

8. **Use `req.hostname` instead of manual `X-Forwarded-Host`.** Express resolves it correctly given `trust proxy` is set.

9. **Capture IP and User-Agent in `expressAuditMiddleware`.** One-liner additions in the `redact`'d details payload.

10. **Sunset webhook query-string secrets.** Add a deprecation log; remove after 60 days.

11. **Tighten registration.** Move whitelist into DB invitation table; add captcha + e-mail verification.

12. **Shorten access-token TTL to 2h + refresh-token rotation.** Or document why 7d is acceptable.

## Code Remediation Examples

### C-002 — Pin JWT algorithm on local-file tokens
```ts
// backend/src/lib/local-file-token.ts
export const signLocalFileToken = (args: { key: string; mimeType: string; expiresInSeconds?: number }) => {
    const expiresInSeconds = Math.max(15, Math.min(60 * 10, Number(args.expiresInSeconds ?? 120)))
    return jwt.sign(
        { kind: 'local-file', key: args.key, mimeType: args.mimeType },
        requireJwtSecret(),
        { algorithm: 'HS256', expiresIn: expiresInSeconds }
    )
}

export const verifyLocalFileToken = (token: string): LocalFileTokenPayload => {
    const decoded = jwt.verify(token, requireJwtSecret(), {
        algorithms: ['HS256']
    }) as any
    if (!decoded || decoded.kind !== 'local-file' ||
        typeof decoded.key !== 'string' ||
        typeof decoded.mimeType !== 'string') {
        throw new Error('Invalid token')
    }
    return decoded
}
```
